# ChargeSafe 项目阶段改进分析报告

> **分析区间**：2026-07-08 → 2026-07-18  
> **对比基线**：`079e1e6`（2026-07-08 19:32，7 月 8 日最后一次合并版本）  
> **当前提交**：`0656eb3`（`feat: harden demo workflows and browser coverage`）  
> **分析口径**：以 Git 差异、源码、Flyway 迁移和本机验证结果为准；本报告描述的是“课程答辩/演示可用”的阶段成果，不等同于生产系统最终交付。

## 一、结论概述

相对 7 月 8 日的版本，ChargeSafe 的提升不只是增加页面和代码量，而是把原来“具备基础业务页面、可以启动”的项目，推进为一套能够围绕真实账号、权限边界、状态流转和多端页面进行演示与验证的系统。

最突出的改进有五点：

1. **安全边界更可靠**：JWT 认证从“认证异常仍可能继续进入接口”的 fail-open 风险，改为失败立即返回 401 的 fail-closed；权限码、路由和数据范围也增加了可执行的约束。
2. **核心业务形成可演示闭环**：预约充电和报修工单不再只停留在页面或单接口层面，已覆盖关键状态迁移、端口状态恢复、同社区派单和物业验收闭环。
3. **三端职责更清晰**：管理端、居民 H5/微信小程序和后端围绕同一套权限与业务数据协作；Mock 只能在开发环境显式开启，避免把模拟结果混同为真实业务数据。
4. **工程质量明显提高**：后端运行基线统一到 Java 21，新增前端浏览器回归、场景数据测试和小程序 API/Mock 测试；目前已有新鲜构建与测试结果支撑演示。
5. **答辩呈现更完整**：新增居民工作台、部门与设备分类管理、三级 3D 大屏和统一视觉风格，使“安全充电运维平台”的业务角色、管理能力与可视化表达形成较完整的叙事。

从 `079e1e6` 到 `0656eb3`，Git 记录显示共有 **235 个受跟踪文件变化、19,368 行新增、4,709 行删除**。其中包含文档、锁文件和构建配置，不能把这个数字简单等同为业务代码增量；但它反映了本阶段同时覆盖后端、管理端、小程序、测试和文档治理的广度。

## 二、与 7 月 8 日基线相比的核心改进

| 维度 | 7 月 8 日基线 | 7 月 18 日阶段状态 | 实际价值 |
| --- | --- | --- | --- |
| 认证安全 | JWT 过滤器遇到缺失或无效 Token 时存在继续放行链路的风险 | 认证失败统一短路为 401，并在请求开始/结束清理 `UserContext` | 减少匿名访问与线程复用残留的安全风险 |
| 权限与数据范围 | 权限码和多角色访问边界缺少系统性回归保障 | 控制器、迁移和前端权限码建立一致性检查；居民、物业、运维等角色按社区/本人范围取数 | 让“谁能看什么、谁能操作什么”可验证，而非只靠页面隐藏 |
| 后端技术基线 | `pom.xml` 仍以 Java 17 为编译目标 | 编译与 Maven 运行均锁定 Java 21，并由 Enforcer 约束 | 本机开发、测试和打包环境一致，避免以低版本兼容配置掩盖问题 |
| 业务能力 | 基础接口与页面已经存在，但关键跨角色链路不完整 | 完成预约—充电—结单、报修—派单—接单—维修—物业验收等关键状态链路加固 | 可用连续流程讲清楚平台如何处理真实运维场景 |
| 管理端表达 | 以常规后台页面为主 | 新增居民工作台、设备分类、部门管理、403 页面和三级 3D 大屏 | 管理与居民两类角色更清楚，演示层次更完整 |
| 小程序接入 | 页面和请求逻辑存在冗余，真实接口与 Mock 的界线不清晰 | API 按认证、充电、订单、车棚、通知、报修拆分；Mock 仅开发环境显式启用 | 降低“开发环境看起来能跑、实际接口不可用”的风险 |
| 测试与构建 | 后端测试源较少；前端没有受跟踪测试 | 后端测试输入从 2 个增至 21 个；Admin 新增 2 个测试文件，小程序新增 4 个测试文件 | 关键行为有可重复的验证入口，而不是只靠手工点击 |

### 2.1 安全与权限：从“能登录”提升到“认证失败不能越过边界”

本阶段最有价值的改进是关闭 JWT fail-open 路径。基线版本中，Token 缺失、格式错误、校验失败等异常虽然不会建立登录上下文，但过滤器仍可能继续执行后续 Controller。当前 `JwtAuthenticationFilter` 已改为：除登录入口外，受保护的 `/api/*` 请求只要缺少或无法验证认证信息，就立即返回统一的 HTTP 401；合法认证但没有业务权限的情形仍交给既有权限切面处理。

这不是单纯修改一个返回码，还配套补了认证 HTTP 测试、权限码一致性测试、居民与管理端大屏路由访问契约测试，以及社区级数据范围测试。居民 Dashboard 不接受客户端传入的社区 ID，而是从 JWT 上下文解析；报修派单候选人也按同社区范围过滤。这些约束使权限控制不再只存在于前端菜单，而是进入接口和数据访问层。

### 2.2 业务闭环：从“功能清单”提升到“可连续演示的状态机”

项目现在可以围绕两个最能体现业务价值的流程进行答辩演示：

- **预约充电闭环**：居民查询可用端口、预约、开始充电、结束充电，订单完成后端口回到 `IDLE`。服务层补充了预约过期、重复操作、状态转换和费用结算等边界处理。
- **报修运维闭环**：报修提交后可审核、生成工单、派单、运维接单和维修、物业验收及关闭。联调记录中，报修单 `#3` 到达 `FINISHED`，工单 `#2` 到达 `CLOSED`，14 号端口恢复为 `IDLE`；居民 H5 端同步显示“已完成”。

这两条链路的意义在于，系统展示的不再是彼此独立的表格页，而是“发现问题—处理问题—结果回写”的业务协同。需要说明的是，上述数据来自本机演示库与联调审计记录，不能表述为真实小区的生产业务数据。

### 2.3 管理端：功能、角色和可视化层次同时增强

管理端新增或完善了居民工作台、设备分类、部门管理和 403 无权访问页，并调整路由守卫和权限加载方式，使平台管理员与居民用户拥有不同的落地页和访问范围。

三级 3D 大屏是本阶段最直观的展示改进。它采用 **Vue 管理页面状态与生命周期、原生 Three.js + three-globe 承担渲染** 的分层结构，形成“地球—社区—车棚/站点”的三级钻取。场景不以模型节点名冒充业务标识，而是显式绑定 `communityId`、`stationId`、`deviceId` 和 `portId`；端口状态也有独立的展示语义。

此前 `EarthView.js` 中的 `pointLabel()` 兼容性问题已迁移至 `labelsData()` API。当前 3D 路由已进入浏览器回归，且本机实际加载记录中没有控制台错误。它适合用于展示数据层级和运维视角，但仍应明确：演示数据和场景坐标不是实时硬件遥测。

### 2.4 小程序：从页面堆叠转向真实接口优先、Mock 可控

小程序 API 被拆分为 `auth`、`charging`、`order`、`parking`、`notification`、`repair` 等模块，统一处理 API 基地址、响应码和认证错误。原先注册、忘记密码、资料编辑、设置及多份冗余 Mock/API 文件被清理，页面结构和 TabBar 也收敛到当前演示真正需要的路径。

更关键的是，Mock 的启用条件被限制为“开发环境且显式设置 `VITE_USE_MOCK=true`”。即使生产环境误配为 `true`，Mock 也保持关闭；模拟响应会携带明确标识。这个设计避免了前端在未连接后端时悄悄显示伪业务结果，是项目工程可信度的重要改进。

本轮已完成 H5 真实账号登录、首页、订单列表和报修列表的浏览器回归；`mp-weixin` 构建已导入微信开发者工具验证，并已按本轮验收记录完成真机验收。当前没有独立的 H5 自动化端到端脚本，这一点应如实保留为后续可增强项。

### 2.5 工程化与可维护性：让改动可以复现、回归和说明

后端已统一使用 Java 21，`maven-enforcer-plugin` 限制 Maven 运行时版本，未引入 preview feature、`--enable-preview`、`--add-opens` 或 `--add-exports` 等规避手段。Flyway 保留基线 V1—V5 不变，并新增 V6（居民工作台权限）和 V7（部门、设备分类及关联权限）作为顺序演进。

本地开发工作流也从 Docker/H2 方向收敛为 Windows 原生 MySQL、Maven、Node.js 与 npm；同时补充环境变量示例、启动脚本、开发指南、当前待办和过程日志。文档按“当前文档”和“归档材料”重新组织，减少了实施计划与现状结论混在一起造成的理解成本。

## 四、突出优点：适合课程答辩呈现的角度

1. **有明确的问题意识，而不是只展示界面**：JWT fail-open 的根因、修复边界和回归测试形成了完整叙述，能体现安全设计能力。
2. **有可讲清的业务闭环**：充电与报修分别覆盖“用户发起—系统状态变化—运维/物业协同—结果回写”，适合用真实演示数据串联展示。
3. **有跨端一致性**：居民在小程序/H5 看到订单和报修结果，管理端承担配置、派单、监管和大屏展示，角色分工自然。
4. **有技术架构取舍**：3D 渲染没有塞进 Vue 响应式体系；Mock 不伪装真实数据；Flyway 历史迁移不被重写。这些选择体现了可维护性和边界意识。
5. **有验证证据**：114 个后端测试、28 条管理端浏览器回归、13 条小程序单测和双端构建结果，可以避免答辩中只有“我试过能跑”的主观表述。

## 五、仍需如实说明的范围与后续方向

当前版本已经具备本地环境下的课程答辩/演示条件，但并不是生产系统的最终版本。以下能力尚未实现，或需要外部条件才能验收：

| 范围 | 当前边界 |
| --- | --- |
| 真实硬件接入 | 尚无真实充电桩、电表、厂商协议或设备告警接入；现有模拟器数据必须明确标识为模拟数据 |
| 支付、短信、地图导航 | 需要第三方平台账号、密钥、回调、计费和风控规则，当前未接入 |
| 生产部署 | 尚缺域名、HTTPS 证书、生产数据库、网络策略、CORS 白名单和上线监控等条件 |
| 自动化深度 | 管理端已有路由级浏览器回归，小程序已有逻辑单测，但 H5 尚无独立端到端自动化脚本；复杂 3D 视觉语义也未做截图级自动化断言 |
| 演示数据 | 本地订单、工单、告警与统计数据用于演示和联调，不应被描述为真实运营数据或实时物联网数据 |

## 六、总体评价

7 月 8 日之后的改进，使 ChargeSafe 从一个具备基础功能的项目，发展为一个在**安全性、业务闭环、多端协同、可视化表达和可验证性**上更完整的阶段性系统。对课程答辩而言，最有说服力的不是新增了多少页面，而是已经能够用“安全认证—权限范围—充电/报修流程—管理端监控—居民端反馈—自动化验证”这条主线讲出一套完整逻辑。

后续若进入生产化阶段，应优先补齐真实设备和第三方服务接入、生产部署治理与更深层的端到端自动化；这些属于外部条件和下一阶段工程，不影响当前作为演示版本的主要价值。
