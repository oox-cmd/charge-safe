# 预约与充电状态机收紧记录

> 日期：2026-07-15

## 问题

后端已有预约、取消、开始、结束和 `reservation_id`，但状态更新是“先查后无条件 updateById”，未检查写入结果。居民可按端口 ID 操作其他社区；存在活动充电时仍可预约/直接开始；管理列表缺少方法权限，本人订单详情没有独立边界；端口缺失时订单仍可完成。

## 根因

业务方法只验证单个对象的当前快照，没有把用户活动状态、社区归属、并发条件和受影响行数纳入同一状态机。管理与居民读取复用通用端点，导致访问语义模糊。

## 红测

在原 15 项 charging Service 测试上先增加 6 项。首次定向运行 21 项，其中 5 项失败：

- 跨社区预约未拒绝；
- 跨社区直接开始未拒绝；
- reservation insert 返回 0 仍返回成功；
- order insert 返回 0 仍返回成功；
- 订单端口缺失仍完成订单。

活动订单测试最初因端口未 stub 产生假阳性，复核调用路径后补齐成功前置，使它能真实验证活动订单互斥；没有把假阳性计为有效红测。

## 修改范围

- 三个 Mapper 增加带期望原状态的原子更新，不改表或迁移。
- Service 增加居民角色、本人、社区、活动状态、用户行锁和关键写入计数校验。
- 预约过期开始使用专用异常，提交 `EXPIRED/IDLE` 清理后返回 6003。
- 管理预约/订单端点复用现有 view 权限并按 DataScope；新增本人预约分页和本人订单详情。
- 增加 21 项 Service 测试和 4 项 HTTP 访问测试。
